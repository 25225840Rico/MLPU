### Hallazgo 1 — HTTP 429 al abrir el detalle
Log capturado:
```
[ML-HISTORY] historial: 10/10 (offset 0)
(error) [ML-BOT] ML historial: /orders/2000017007883684 HTTP 429
```
Causa: `attachReceiverNames` (worker/ml-history.js) resolvía el nombre real del
comprador con `GET /shipments/{id}` para las 10 órdenes **en paralelo**
(`Promise.all` sin escalonar). Esa ráfaga dejaba la cuenta rate-limited, así que
la siguiente `GET /orders/{id}` (en `getOrderDetail`, al abrir el detalle) caía
con 429. `mlGet` no reintentaba: lanzaba `httpError` → `withMlGuard` mostraba
"❌ Error consultando ML… HTTP 429".

Fix (worker/ml-history.js):
- `mlGet(token, path, { retries = 3 })`: bucle con reintento ante 429/503.
  Respeta el header `Retry-After` si viene; si no, backoff exponencial corto
  `Math.min(2000, 300 * 2**attempt)` (0.3 / 0.6 / 1.2 s). Loguea cada reintento.
- `attachReceiverNames`: `await sleep(i * 60)` antes de cada llamada (escalona la
  ráfaga 0,60,120…540 ms) para no gatillar el 429 de entrada.

Desplegado Version 3e4350d2. Re-test: el detalle abrió **sin 429** (logs
11:15:35→55 sin un solo `(error)`).

### Hallazgo 2 — "Mensajear no hace nada" (el de verdad)
Tras el fix del 429, el detalle abría pero "💬 Mensajear" seguía sin mostrar el
prompt, y NO había error en logs. La rama `msg:` no llama a ML (solo `setPending`
+ `tgSend`), así que el síntoma (POST sin log, sin error, sin prompt) no cuadraba.

Se añadió log de diagnóstico temporal a la entrada de `handleCallback`:
`log('callback recibido:', JSON.stringify(data), 'chat', chatId)`. Deploy da727130.
Captura:
```
[ML-BOT] callback recibido: "msg:2000017007883684" chat 1036420688
```
→ El `callback_data` ERA correcto y la rama `msg:` (telegram-bot.js:330) sí se
ejecutaba. El problema: la línea final era
`return void tgSend(env, chatId, '✍️ Escribí el texto…')`. El operador **`void`
descarta la promesa** de `tgSend`. Como `handleCallback` se ejecuta con `await`
pero esa rama retorna `undefined` de inmediato (sin esperar el envío), el Worker
completaba `await work`, respondía 200 y el `fetch` a Telegram quedaba en vuelo →
se cortaba. Racy: a veces alcanzaba a mandarse, a veces no. Es el mismo origen
del bug que antes se atacó con `ctx.waitUntil` (cambiado a `await work`), pero
quedó este resto con `void`.

El patrón estaba en **>30 sitios** del archivo (todos `return void tgSend(...)`).
Donde "funcionaba" era porque el envío iba dentro de un helper con `await tgSend`
cuya promesa se retornaba y se esperaba aguas arriba.

Fix (worker/telegram-bot.js): replace_all `return void tgSend(` → `return tgSend(`
(retorna la promesa para que la cadena `await handleCallback`/`await work` la
espere). Ningún caller usa el valor de retorno → cambio seguro. Verificado por
grep que no quedaran `tgSend(` flotantes (todos `await`/`return`).

Desplegado Version c4faacb8. El usuario confirmó: **apareció el prompt**.

nada" (solo escaneó), y apareció HTTP 429. Tail en vivo (wrangler tail mlpu-proxy)

fecha 2026-06-17, ya delivered). La venta de HOY NO está en el KV.
Flags de esa orden: prep_msg_sent=false/prep_warned=true, ig_cta_sent=false/
ig_cta_warned=true → los mensajes se INTENTARON y FALLARON.

Causas reales (ninguna es bug simple):
1) Rate-limit 429: el tail mostró `GET /shipments/.. 429`, `GET /users/me 429`,
   `sendBuyerMessage (preparación) falló HTTP 429`. El reintento de 429 solo
   estaba en ml-history.js; el resto (scheduler, tracking, messaging) llamaba a
   ML con fetch crudo. FIX: helper compartido worker/ml-fetch.js (mlFetch,
   reintenta 429/503, Retry-After, backoff) aplicado en tracking.js, scheduler.js,
   messaging.js, ml-messaging.js, index.js. Commit 9ebeae8, Version 1d596da0.
2) ML bloquea al vendedor: `blocked_by_conversation_initiated_by_seller_limited`
   (también en la evidencia y en "reseña + IG"). Política ML NEWBIE: el vendedor
   no puede iniciar conversación hasta que el comprador responda. Action Guide no
   ofrece FREE_TEXT para ese pack → cae a clásico → bloqueado. NO es código.
3) Órdenes no entran al KV: solo se registran por notificación orders_v2 →
   /ml/notifications → processOrderNotification. La de hoy no llegó/no se procesó
   (quizá por 429, ya mitigado). Sin la orden en KV: la foto no matchea (pending=0)
   y el scheduler no la ve. Además `tracking ML ... Invalid parameters for shipping
   mode` = la orden es drop_off (ME2); ML no acepta PUT tracking en ME2 (esperado,
   el tracking lo pone ML).
