# 2026-07-10 — Sesión 11: máxima categoría + envío siempre por comprador

## Pedido del usuario
"automl sube todas las publicaciones a la maxima categoria y todas con envio
pagado por el comprador" → instrucción: todo lo publicado debe salir en el
listing_type de máxima exposición (Premium/gold_pro) y con envío a cargo del
comprador, sin opción de envío gratis.

## Estado previo (lo contrario en ambos ejes)
- `pickListingType` (worker/publisher.js) elegía lo MÁS BARATO:
  `['free','gold_special','gold_pro']`, fallback 'free'.
- Envío por comprador era solo el DEFAULT: `draft.freeShipping` alternable
  con el botón `cat:ship:` de la vista previa del bot.
- SPA (src/App.jsx): `listingType` default 'free' en 3 puntos.

## Cambios aplicados

### worker/publisher.js
- `pickListingType`: preferencia `['gold_pro','gold_special','free']`;
  fallback ante fallo de `available_listing_types` → 'gold_pro' (si la
  categoría no lo soporta, ML devuelve error y el bot lo muestra con botón
  Reintentar; caso raro). Comentario actualizado con la decisión.
- `createListing`: `shipping: { mode:'me2', free_shipping:false,
  local_pick_up:false }` fijo (nota: el docstring del archivo YA decía
  "shipping SIEMPRE free_shipping:false"; el código había derivado con el
  toggle — ahora vuelven a coincidir).
- `estimateProfit`: eliminado el bloque de `shipping_options/free` (solo
  corría con freeShipping=true, que ya no existe). Devuelve
  `{ listingType, fee, net: price - fee }` (ya no retorna `ship`).

### worker/telegram-bot.js
- Eliminado el handler `cat:ship:` (líneas 518-525) y el botón
  "🚚 Cambiar a envío gratis (vendedor)" del teclado de la preview.
- Eliminado `freeShipping: false` del draft inicial.
- Preview: línea fija "🚚 Envío: a cargo del comprador"; la línea de
  ganancia ahora muestra el tipo real: `{gold_pro:'Premium',
  gold_special:'Clásica', free:'gratuita'}` (antes decía "Clásica/paga").
- Mensaje post-publicación: "envío a cargo del comprador" fijo.
- Ayuda: "Publicación Premium, envío a cargo del comprador y stock 1."

### src/App.jsx (SPA legacy, sigue operativo)
- Default `gold_pro` en: `useState`, borrador nuevo (`editQty:3` line ~728),
  `setListingType(draft.listingType || 'gold_pro')` y
  `listing_type_id: draft.listingType || 'gold_pro'`.
- El selector manual de 3 pestañas (Gratuita/Clásica/Premium) y el toggle de
  envío gratis del SPA SIGUEN existiendo — solo cambió el default. En el bot
  de Telegram en cambio la regla es fija (sin UI para cambiarla).

# 2026-07-10 (parte 2) — Migración masiva del inventario a Premium + envío por comprador

## Pedido
"subelas todas a la categoria mas alta ahora, pero no en el bot sino en todo
el inventario actual con envio a pagar por el comprador, y actualiza el excel".

## Cómo se hizo
- El token de KV estaba vencido (~20 h) → se usó el PROXY del Worker
  (`https://mlpu-proxy.aronricocl.workers.dev/ml/<ruta>`), que inyecta y
  refresca el token solo. No se rotó el refresh_token localmente.
- Script `upgrade-inventory.mjs` (scratchpad de la sesión; lógica descrita
  aquí): por cada ítem del seller 283388639:
  1. GET /items/{id} (estado previo)
  2. GET /items/{id}/available_upgrades → POST /items/{id}/listing_type
     con el mejor disponible (ranking free<...<gold_special<gold_premium<gold_pro)
  3. PUT /items/{id} shipping {mode existente, free_shipping:false, local_pick_up}
  4. RE-GET para verificar el valor real (no confiar en el 200)
  5. GET listing_prices para la comisión real del nuevo tipo
- Smoke test previo con MLC4146267638 (Clásica→Premium OK, envío OK).
- Concurrencia 5, reintentos con backoff en 429.

## Resultado (160 ítems: 144 active, 11 paused, 5 under_review)

  upgrade fue aceptado).
- **Envío por comprador: 109/160.**
- **51 ítems con precio ≥ $19.990: ML mantiene free_shipping=true** aunque
  el PUT devuelve 200 → envío gratis OBLIGATORIO de MLC confirmado
  empíricamente (min price forzado = exactamente 19990). No es corregible
  por API; el costo corre por el vendedor.
- **1 falla real**: MLC1986993239 (under_review, sub_status forbidden) —
  PUT shipping rechazado "Cannot update item ... status:under_review".
  Ya era gold_pro; corregir envío cuando salga de revisión (tarea abierta).

# 2026-07-10 (parte 3) — Intento de liberar el envío gratis forzado (≥$19.990)

Pedido: no bajar precios; bajar de categoría o buscar otra vía para que el
comprador pague el envío en los 51 ítems forzados.

Experimentos sobre MLC4044512534 ($19.990, envío gratis forzado), verificando
siempre el valor real re-leído (no el status HTTP):
1. Premium + shipping mode 'custom' con costo al comprador → 200, IGNORADO
   (sigue me2 + tag mandatory_free_shipping).
2. Premium + mode 'not_specified' (a acordar) → 200, IGNORADO.
3. Downgrade a gold_special (Clásica) OK + PUT free_shipping:false → 200,
   IGNORADO (el tag mandatory_free_shipping aplica igual en Clásica).
4. Downgrade a 'free' → 400 "Is not possible to downgrade... new_listing_type_id:[]"
   (ML no ofrece ningún tipo inferior para el ítem).
5. shipping_options/free: costo del envío para el VENDEDOR = $6.300 idéntico
   en gold_special y gold_pro (a $19.990 y a $33.990) → bajar de categoría
   tampoco ahorra nada.

CONCLUSIÓN: el envío gratis obligatorio a precio ≥ $19.990 en MLC es regla
dura del marketplace: aplica a TODOS los listing_types alcanzables y ML
revierte en silencio cualquier intento por API. Sin bajar el precio bajo
$19.990 NO existe forma de que el comprador pague el envío. El ítem de
prueba quedó RESTAURADO a gold_pro (verificado). Los 51 ítems permanecen en
Premium con envío gratis; el vendedor paga ~$6.300 por venta (mitigable solo
subiendo el precio, que el usuario no pidió).
